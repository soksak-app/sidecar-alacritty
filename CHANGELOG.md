# Changelog

- S79: OSC 7 rejects a URI of another scheme, such as `kitty-shell-cwd://`, with an explicit error: only `file` URIs are accepted, as the terminal protocol spec states.
- S78: A synchronized update (DEC 2026) that is never closed ends at its deadline, 150 ms after its opening sequence: the frame clock calls `stop_sync`, the held output is drawn, and the timer exists only while an update is held.
- S77: Inline images keep moving with output at the history limit: the scroll generation counts the rows that the limit dropped, and the rows of every input are counted in slices of 999 bytes, so a flood recycles the cached rows without an allocation per row.
- S76: A malformed color of OSC 4 and a malformed target, data or encoding of OSC 52 produce `sequence.rejected` with a fixed reason that does not hold the payload, instead of only a debug line.
- S75: One `vte::Parser` finds the sequences before the terminal, so an OSC ended by CAN, SUB or ESC no longer holds later output or marks, an erase with a control byte inside it erases in place, an unknown CSI, DCS or ESC produces `sequence.rejected` without its payload, and a sequence over 1402200 bytes is rejected.
- S84: An inline image scrolled partly past the top edge stays visible until its last row leaves the frame: the top of an image is signed, and the store keeps the height at which the frame draws it.
- S83: A valid inline image past an edge of the frame draws clipped, and an image wholly outside the frame draws nothing, so the frame draws instead of failing with `Frame draw failed`.
- S81: An inline image is decoded with ImageIO when it is stored: an image that does not decode is rejected with `sequence.rejected` and no image, and the frame draws without it, instead of failing the whole frame with `Frame draw failed`.
- S80: A request line has the 64 MiB message limit: a line over it is refused with `message exceeds 67108864 bytes` and ends the input of its connection, because the line reader stops after a decoder error.
- S86: A reconnect reports the input that the session holds, because the session reports it only when the state changes.
- S74: Closing a session ends the jobs of its shell; the behavior landed with S73-5, and its three tests pass.
- S85: The job test waits for the report of its job instead of a timer, and the exit test waits for the refusal of a signal without a time budget.
- S73-6: The surface consumes one chunk of output per turn, so an input request ends during a flood of output.
- S73-5: Close follows the table of the specification: queued input completes with `session closed`, a close that is requested decides the reason when the reaper reports the child, and close sends SIGHUP to the child before the SIGKILL of its group and child.
- S73-4: The end of a child sends its last output before `Exit`, fails queued input with `child exited`, closes the masters, and the surface draws the screen that the frame clock holds before it ends.
- S73-3-1: The bound of queued input is checked under the queue lock, so a concurrent write is never refused for bytes that another write takes back; a test session sets its bound with `PtyService::with_input_bound`.
- S73-3: Queued input has a bound of 64 MiB: input of a person over it is refused with an explicit error, and a reply of the engine stops reads and reports `input_held`.
- S82: The default of a lost write result states its reason, so the sources pass the census of `make test`.
- S73-2: One I/O task reads and writes a session: reads stop at 16 chunks of 64 KiB, a write never waits in the surface task, and the surface acknowledges a write from its result.
- S73-1: The session holds no ring and no attach path, so output that the consumer read leaves no copy; a connection that is not persistent closes its sessions when it ends.
- S21: The cost of a frame on 0.0.4 is measured: a status line 1.6 ms per frame and 20 rows 3.1 ms per frame.
- S20: Version 0.0.4, which carries S19.
- S19: Output that the frame clock holds builds no screen.
- S1-5: The comparison with the VT sidecar is measured: a frame of a status line takes 1.5 ms of application CPU against 12.4 ms, and a frame of 20 rewritten rows takes 4.1 ms against 14.6 ms.
- S1-17: The sidecar is released as 0.0.3.
- S1-18: The sidecar uses the records kit 0.0.6.
- S1-16: The start record and the stall dump of the service name the sidecar `alacritty`.
- S1-15: `make test` runs every frame test of the diagnostics build.
- S1-14: `make frame-benchmark` measures the CPU time and the footprint of a built service.
- S1-13: A frame draws without a GPU pass, which lowers the memory of a loaded service from 196 MB to 40 MB at the same CPU time.
- S1-12: The sidecar is released as 0.0.2 and listed in the registry.
- S1-11: The image surface of a session draws on the GPU frame, which redraws only the rows that changed.
- S1-9: A cell of the screen holds its colors as RGB bytes and its grapheme inline, so building the screen of a frame takes no allocation per cell.
- S1-8: A frame whose record the event log does not store is not hashed.
- S1-6: The process group test waits for the exit stage at which macOS refuses signals.
- S1-4: The sidecar is public as `soksak-app/sidecar-alacritty`, released as 0.0.1 and listed in the registry.
- S1-7: A drawn frame sends a `view` event with its cursor, caret and scrollback when they change.
- S1-4-2: A test runs the pre-push hook and checks its pushed range instead of matching its text.
- S1-4-1: The pre-push hook checks every pushed commit on the first push of a repository.
- S1-3: A frame sends no screen message; `screen.read` answers the full screen.
